# SOOYA 每日照片连续性完整方案

> 状态：方案文档；不包含连续性功能实现、部署或服务重启
> 日期：2026-08-22
> 开发分支：`feat/daily-visual-continuity`
> 代码基线：GitHub `main`（`9ab01e5`）+ M365 单参考图补丁（`f0e2b53`）
> 适用范围：聊天内自拍、主动发送的 `selfie` / `lifestyle` 动态照片（两者都是 SOOYA 本人出镜图片，都进入当天 outfit continuity）；`pov` 仅为历史数据兼容值，主动链路已不再生成；聊天内普通纯场景图只约束活动与地点，不强行加入人物穿搭

> 2026-08-22 更新：主动消息配图已从 POV 改造为 lifestyle（见 `docs/SOOYA-PROACTIVE-LIFESTYLE-IMAGE-PLAN.md`）。
> 主动图片类型现在只有 `selfie` 与 `lifestyle`，两者都必须加载人物参考并共享同一套当天视觉连续性状态；
> 历史已保存的 `pov` Moment 仍可读取，但不再生成。下文与该决定冲突的 POV 描述按此更新为准。

## 0. 当前项目基线

本方案按当前服务器源仓库 `/opt/sooya/src` 的真实代码编写，不按抽象项目假设设计。

现有链路已经具备：

- `Replier`：处理聊天内 `selfImagePrompt` / `imagePrompt`，自拍会加载人物参考图；
- `ProactiveComposer.prepareMedia`：处理主动动态中的 `selfie` / `lifestyle`（均为人物出镜图片），并使用真实候选活动和事件地点；
- `MediaDirector.image`：把单次图片意图扩写为 Image2 Prompt；
- `ImageDirectorSchema`：当前只返回 `prompt` 与 `aspectRatio`；
- `SettingsRepo`：已有通用 JSON `get/set/delete`，可持久化当天状态；
- `Life` / `World`：已有当前活动、地点、时间与世界快照；
- `LIFE_TIME_ZONE`：已有 IANA 时区配置，默认 `Asia/Shanghai`；
- `MediaStore`：两条图片链路都在生成成功后保存媒体和元数据；
- `PersonaReferenceLoader`：保证人物身份参考，但它本身不保证服装连续。

当前缺口是：聊天自拍与主动自拍每次都让图片导演独立描述服装，没有共享、持久化的“今天穿什么”状态；聊天自拍也没有把 `Life` 当前活动作为生成前的权威约束。M365 补丁只解决单参考图经 `/images/edits` 生成及 `b64_json` 返回格式，不解决穿搭或生活连续性。

## 1. 背景与问题

当前连续两张照片分别使用了“简单的休闲外套”和“黑色外套”等不同提示词。虽然人物身份参考保持一致，但每次图片生成都只看到本次场景，没有读取“今天已经穿了什么、正在做什么、在哪里”的持久状态，因此图片导演会重新设计服装，造成同一天、相邻时间、同一段活动中的穿搭跳变。

现有链路中，聊天自拍和主动动态已经能获得部分当前活动信息，但缺少统一的“每日视觉连续性状态”；媒体记录保存了原始请求提示，却不足以稳定复用最终穿搭。

## 2. 目标与原则

### 2.1 核心目标

1. 同一自然日内，SOOYA 默认延续已经确定的完整穿搭。
2. 相邻照片中的活动、地点、时间段与生活状态保持一致，不凭空跳转。
3. 合理场景允许换衣服，但换装必须有明确原因并形成新的连续状态。
4. 服务重启后仍记得当天穿搭，避免“重启失忆”。
5. 聊天自拍和主动动态使用同一套规则，避免两条链路互相打架。

### 2.2 设计原则

- **生活状态优先**：当前真实活动、地点高于临时生成提示词。
- **同日默认锁定**：已有穿搭时，普通场景变化不重新设计衣服。
- **合理换装是例外**：只有明确指令或可解释的生活转换才允许换装。
- **生成成功后提交**：图片生成或保存失败时，不更新连续性状态。
- **约束最后注入**：最终送给图片模型前再次附加硬约束，防止中间导演改写。
- **只有人物本人出镜的照片才维护穿搭**：主动链路只剩 `selfie` / `lifestyle` 两个人物出镜类型；聊天内真正的纯场景图不强行加入人物穿搭。

## 3. 产品规则

### 3.1 每日边界

- 使用 SOOYA 的生活时区计算自然日，建议沿用 `LIFE_TIME_ZONE`。
- 日期变化后，前一天状态不再强制锁定。
- 新一天第一张人物照片确定当天初始穿搭；之后默认复用。

### 3.2 默认连续规则

当以下条件同时成立时，下一张人物照片必须使用完全相同的穿搭：

- 是同一自然日；
- 已有成功生成并保存的穿搭状态；
- 用户没有明确提出换装；
- 当前活动不属于合理换装转换；
- 没有显式的剧情或生活事件要求换装。

“相同穿搭”至少锁定：

- 外套/上衣；
- 内搭；
- 下装；
- 鞋子；
- 主要颜色；
- 明显材质、版型和层次；
- 场景中可见的关键配饰。

允许因构图不可见而省略某些单品，但不允许把未拍到理解成已经换装。

### 3.3 合理换装场景

换装解锁分为两类。

#### A. 用户明确要求

例如：

- “换件衣服再拍”；
- “穿裙子/西装/睡衣”；
- “把外套脱了”；
- “换成运动服”；
- “今天第二套穿搭”。

用户明确要求优先级最高。生成成功后，新穿搭覆盖当天当前状态，后续继续沿用。

#### B. 生活场景自然转换

可允许换装的典型场景：

- 洗澡、淋浴前后；
- 睡觉、起床、睡醒；
- 健身、跑步、瑜伽等运动前后；
- 游泳、泡温泉等需要专用服装的活动；
- 上班、上学、正式聚会、宴会等明确着装要求；
- 回家后明确进入居家休息状态；
- 天气或环境出现足以改变外层服装的显著变化。

这些场景只是“允许”换装，不代表必须换。图片导演仍应选择合理结果，并说明换装原因供元数据记录。

### 3.4 不应触发换装的普通变化

以下变化默认继续穿同一套衣服：

- 从街上走到图书馆；
- 散步、买咖啡、吃饭、逛店；
- 同一外出行程中的地点切换；
- 拍摄角度、光线、天气描述变化；
- 模型临时写出“白裙子”“黑色外套”等新衣服，但用户和生活状态都没有换装依据。

特别是“去图书馆路上”不应导致换装；它只应该更新活动/地点背景。

### 3.5 活动与地点连续规则

最终图片提示必须包含权威的当前状态：

- 当前活动；
- 当前活动类型（在家、外出、睡眠等）；
- 当前地点或地点类型；
- 必要时包含时间段和天气。

优先级建议为：

1. 用户本轮明确指令；
2. 当前 Life/World 实时状态；
3. 已保存的最近照片连续状态；
4. 图片导演自行补全。

若用户说法与生活状态冲突，应先判断用户是在要求新活动，还是只是在问/评价；不能仅因一句普通对话就改写活动。

“活动统一”不等于一整天只能做一件事。活动应随 `Life` 的真实状态正常变化，但同一个活动段内的连续照片必须一致：

- 没有 Life 转换或用户明确发起的新活动时，不凭图片提示词跳到其他事情；
- Life 已从“去图书馆路上”切到“在图书馆看小说”时，照片可以自然推进；
- 地点变化必须能由当前活动或最近一次合法转换解释；
- 单纯换角度、换构图、再发一张，不创建新的活动段。

## 4. 状态模型

建议新增轻量级 `ImageContinuityService`，使用现有通用设置存储，不新增数据库表和迁移。

### 4.1 持久状态

```ts
interface DailyImageContinuityState {
  version: 1;
  dateKey: string;              // 按 LIFE_TIME_ZONE 计算的 YYYY-MM-DD
  outfit: {
    fullDescription: string;    // 完整、可复用的穿搭描述
    outerwear?: string;
    top?: string;
    bottom?: string;
    shoes?: string;
    accessories?: string[];
  };
  outfitRevision: number;
  activity: string | null;
  activityKind: string | null;
  activityStartedAt: string | null;
  location: string | null;
  scene: string;
  changeReason: string | null;  // user_request / shower / sleep / exercise / formal / etc.
  sourceMediaId: string | null;
  updatedAt: string;
}
```

建议设置键：`image.dailyVisualContinuity.v1`。

### 4.2 本次生成的临时决策

```ts
interface PreparedImageContinuity {
  dateKey: string;
  currentActivity: string | null;
  currentActivityKind: string | null;
  currentLocation: string | null;
  previousOutfit: string | null;
  previousActivity: string | null;
  previousScene: string | null;
  outfitMode: 'new_day' | 'locked' | 'layer_adjustment' | 'full_change';
  changeReason: string | null;
}
```

临时决策只用于本次生成；只有成功生成并保存媒体后才提交为持久状态。

## 5. 核心服务职责

`ImageContinuityService` 建议提供以下能力：

```ts
prepare(input): PreparedImageContinuity
applyToPrompt(prompt, decision): string
commit(decision, result): void
current(): DailyImageContinuityState | null
```

### 5.1 `prepare`

输入：本次场景、是否自拍、用户原始文本、当前活动、活动类型、地点、当前时间。

职责：

1. 计算当天日期键；
2. 读取当天已有状态；
3. 判断是否为人物出镜；
4. 判断用户是否明确要求换装；
5. 判断活动是否属于合理换装转换；
6. 形成“锁定原穿搭”或“允许新穿搭”的决策；
7. 不在此阶段写入状态。

穿搭决策使用四种明确状态，避免多个布尔值组合出矛盾结果：

- `new_day`：当天首张人物照片，建立第一套穿搭；
- `locked`：完整复用当前穿搭；
- `layer_adjustment`：只允许基于温度、室内外转换增减外层，内搭和下装不变；
- `full_change`：明确换装或睡眠、洗澡、运动等场景允许重新确定整套衣服。

### 5.2 `applyToPrompt`

在所有导演改写、动态约束之后，把权威信息追加到最终图片提示末尾。

锁定穿搭时示例：

```text
Real current activity (hard continuity constraint): walking to the library.
Real current location (hard continuity constraint): on the route to the library.
Same-day outfit continuity (hard constraint): Sooya is wearing exactly:
black lightweight casual jacket, light simple inner top, dark straight-leg trousers,
and white casual shoes. Do not change colors, materials, layers, or garment types.
```

允许换装时示例：

```text
A reasonable outfit change is allowed because the activity changed to exercise.
Choose one concrete full outfit appropriate for the scene. This successful outfit
becomes the new same-day continuity state.
```

### 5.3 `commit`

仅在以下条件全部满足后写入：

- 图片生成成功；
- 媒体文件保存成功；
- 已获得媒体 ID；
- 是 SOOYA 本人出镜的照片；
- 最终穿搭描述非空且通过基本校验。

若本次锁定原穿搭，则保存同一穿搭并只更新活动、地点、场景和时间；若本次合理换装，则以新穿搭覆盖当前状态并记录原因。

### 5.4 并发与竞态

聊天自拍和主动自拍可能在相近时间同时生成。若两次都在“当天尚无状态”时独立生成，会各自选出不同衣服。因此同一个 `ImageContinuityService` 需要提供进程内串行锁：

1. 人物自拍开始前取得锁；
2. 在锁内读取状态、形成决策、生成并保存媒体；
3. 成功则提交，失败则不提交；
4. 最后释放锁，让下一张重新读取最新状态。

当前 SOOYA 是单服务进程，这一方案足够；若以后改为多实例，再把锁升级为数据库租约或 CAS。聊天内纯场景照不占用穿搭锁（主动链路已无纯场景类型）。

## 6. 图片导演协议调整

### 6.1 输入扩展

为图片导演增加可选连续性上下文：

```ts
interface ImageDirectorContinuity {
  currentActivity?: string;
  currentLocation?: string;
  previousOutfit?: string;
  outfitMode: 'new_day' | 'locked' | 'layer_adjustment' | 'full_change';
  changeReason?: string;
}
```

### 6.2 输出扩展

图片导演除 `prompt` 和 `aspectRatio` 外，返回规范化的完整穿搭：

```json
{
  "prompt": "最终场景提示",
  "aspectRatio": "3:4",
  "outfit": "黑色轻便休闲外套、浅色简洁内搭、深色直筒长裤、白色休闲鞋"
}
```

规则：

- 人物自拍必须返回具体穿搭；
- 锁定状态下必须原样复用既有穿搭，不得自由改写颜色和单品；
- 允许换装时必须给出完整的新穿搭；
- 纯场景图可以不返回 `outfit`（主动链路已无纯场景类型）。

### 6.3 降级路径

当导演模型失败或返回无效 JSON 时：

1. 仍使用原始场景生成；
2. 继续追加活动、地点硬约束；
3. 若已有当天穿搭，直接追加原穿搭硬约束；
4. 若是当天第一张自拍且无法提取穿搭，使用稳定的默认完整穿搭，不让状态为空；
5. 不因导演失败而跳过连续性规则。

## 7. 两条生成链路的接入方案

### 7.1 聊天自拍

建议流程：

1. 回复规划器产生自拍场景；
2. 读取当前 Life 与 World 状态；
3. `ImageContinuityService.prepare(...)`；
4. 图片导演结合本次场景和连续性决策生成提示；
5. 原有身份参考图继续用于人物一致性；
6. `applyToPrompt(...)` 在最终一步追加硬约束；
7. 调用图片模型；
8. 保存媒体，并在元数据中写入最终导演提示、穿搭和连续性决策；
9. 保存成功后 `commit(...)`。

### 7.2 主动动态（selfie / lifestyle）

流程与聊天自拍一致，但活动和地点以主动事件候选携带的真实状态为准：

1. 主动事件先确定实际活动、地点和场景；
2. `selfie` 与 `lifestyle` 都是人物出镜图片，都调用连续性服务、都加载人物参考图；`lifestyle` 额外要求 SOOYA 本人在画面中自然进行当前活动（禁止纯风景、纯食物、纯桌面、纯物件与第一视角 POV）；模型若误返回旧 `kind=pov`，会在进入生图链路前自动归一化为 `lifestyle`；
3. 动态专属构图约束完成后，再追加连续性硬约束；
4. 图片保存成功后提交状态。

### 7.3 历史 POV 与聊天内纯场景照

- 历史 `pov` Moment 保留可读，但主动链路不再生成；
- 聊天内普通纯场景照保持活动、地点、时间和天气连续；
- 纯场景照不创建或覆盖穿搭状态；
- 若画面偶然出现人物且无法确认是 SOOYA，不提交穿搭。

## 8. 媒体元数据

每张人物照片建议记录：

```json
{
  "prompt": "用户/规划器原始场景",
  "directorPrompt": "实际送给图片模型的最终提示",
  "selfie": true,
  "continuity": {
    "dateKey": "2026-08-22",
    "outfit": "完整穿搭描述",
    "outfitMode": "locked",
    "outfitRevision": 1,
    "changeReason": null,
    "activity": "去图书馆路上",
    "location": "去图书馆的小路"
  }
}
```

这样后续可以解释“为什么这张换装了”，也便于排查模型是否忽略硬约束。

## 9. 换装判断策略

建议采用“确定性规则为主、模型理解为辅”。

### 9.1 明确用户意图

优先识别：换、穿、脱、外套、裙子、西装、睡衣、运动服、泳衣、第二套穿搭等词及其语义变体。

需要避免误判：

- “你穿的是什么”是询问，不是换装指令；
- “怎么衣服不一样”是纠错，不是要求再换一次；
- “黑色外套挺好看”是评价，默认继续穿。

### 9.2 场景转换白名单

建议以可审计白名单判断：

| 类别 | 例子 | 是否允许换装 | 说明 |
|---|---|---:|---|
| 睡眠 | 睡觉、起床、睡醒 | 是 | 睡衣/日常服之间转换 |
| 清洁 | 洗澡、淋浴 | 是 | 清洁前后自然换装 |
| 运动 | 健身、跑步、瑜伽 | 是 | 运动服有功能需要 |
| 水上活动 | 游泳、温泉 | 是 | 专用服装 |
| 正式活动 | 上班、宴会、正式聚会 | 是 | 明确着装要求 |
| 回家休息 | 明确换居家服 | 是 | 需有活动状态支撑 |
| 普通外出 | 图书馆、咖啡店、散步 | 否 | 同一行程延续 |
| 拍摄变化 | 角度、光线、构图变化 | 否 | 不应影响穿搭 |

### 9.3 冲突处理

- 用户明确要求换装时，覆盖默认锁定。
- 用户明确要求保持同一套时，即使场景允许换装也继续锁定。
- 场景提示临时出现新衣服，但没有用户/生活依据时，丢弃新衣服描述并使用已锁定穿搭。
- 活动状态不完整时采取保守策略：继续原穿搭。

## 10. 首次上线时的当天状态处理

因为今天已经存在两张穿搭不一致的照片，首次上线需要选择一个基准。建议以**最近一张成功照片**为准，并人工写入明确的完整穿搭：

> 黑色轻便休闲外套、浅色简洁内搭、深色直筒长裤、白色休闲鞋。

理由：最近一张提示明确包含“黑色外套”，且它代表当前最新视觉状态。写入后，当天后续普通照片继续沿用；进入合理换装场景时再更新。

如果不希望人工初始化，也可让上线后的第一张新自拍成为基准，但这样无法保证它和现有最近一张保持一致，不推荐。

## 11. 代码落点建议

以下仅为实施时的文件级计划，本方案不执行修改。

| 文件/模块 | 建议变更 |
|---|---|
| `core/image-continuity.ts` | 新增每日视觉连续性服务、换装判定、提示注入和提交逻辑 |
| `core/director/schemas.ts` | 图片导演输出增加可选 `outfit` 字段 |
| `core/director/prompts.ts` | 增加同日穿搭、活动地点和换装理由规则 |
| `core/mediaDirector.ts` | 接收连续性上下文，返回规范化穿搭，降级时仍应用硬约束 |
| `core/replier.ts` | 聊天自拍生成前准备连续性，保存成功后提交状态 |
| `core/proactive.ts` | 主动 `selfie` / `lifestyle` 使用同一服务并加载人物参考；不再生成 POV |
| `app.ts` | 创建服务实例并注入聊天、主动生成两条链路 |
| `test/image-continuity.test.ts` | 新增核心规则单元测试 |
| 相关导演/回复/主动生成测试 | 增加集成与回归覆盖 |

`Replier` 仅在 `plan.selfImagePrompt` 且不是用户图片编辑时进入人物连续性流程；普通 `plan.imagePrompt` 和用户上传图片编辑不能覆盖 SOOYA 的当天穿搭。`ProactiveComposer` 的 `selfie` 与 `lifestyle` 都进入人物连续性流程（见 §7.2）。

## 12. 测试方案

### 12.1 单元测试

至少覆盖：

1. 当天第一张自拍没有旧状态，不锁定旧穿搭；
2. 第一张保存成功后，同日第二张默认锁定完全相同的穿搭；
3. 普通地点变化不允许换装；
4. “换成运动服”允许换装；
5. 洗澡、睡觉、运动、游泳等转换允许换装；
6. “怎么衣服不一样”不被误判为换装请求；
7. 用户明确说“不要换衣服”时强制保持；
8. 日期跨天后不继承前一天硬锁；
9. 生成失败不提交新状态；
10. 媒体保存失败不提交新状态；
11. 主动图片（selfie/lifestyle）都覆盖人物穿搭连续；历史 pov 行只读不影响状态；
12. 服务重启后从设置中恢复当天状态；
13. 导演模型失败时仍把旧穿搭注入最终提示；
14. 旧状态数据损坏时安全忽略并重建，不影响发图。
15. 聊天自拍与主动自拍并发时只建立一套初始穿搭；
16. 室内外温度变化只增减外层，不随机替换整套衣服；
17. 用户图片编辑不读取或覆盖 SOOYA 穿搭状态；
18. Life 活动合法推进时背景更新，但同一活动段内不凭提示词跳转。

### 12.2 集成测试

#### 场景一：普通连续外出

- 第一张：早晨街上，黑色休闲外套；
- 第二张：去图书馆路上；
- 第三张：图书馆座位上。

预期：三张人物照片完整穿搭一致，活动和背景依次合理变化。

#### 场景二：合理运动换装

- 图书馆返回；
- 用户说去健身；
- 生成运动自拍。

预期：允许换成具体运动服；后续健身房照片继续沿用运动服。

#### 场景三：洗澡后居家

- 健身后回家；
- 进入洗澡状态；
- 生成洗澡后的居家自拍。

预期：允许换成居家服/睡衣，新穿搭成为当前状态。

#### 场景四：模型试图擅自换衣

- 已锁定黑色外套；
- 中间导演输出“白色裙子”。

预期：最终硬约束覆盖导演的随机衣服，生成请求仍使用黑色外套。

### 12.3 回归测试

- 人物身份参考图仍正常生效；
- 用户提供参考图的编辑流程不被破坏；
- 无图片导演时仍能生成；
- 主动动态与普通聊天文字回复不受影响；
- 现有图片提供方、比例和媒体存储行为不变；
- 所有现有媒体、导演、回复和主动生成测试继续通过。

## 13. 观测与诊断

建议为每次人物图片生成记录结构化日志：

- 日期键；
- 是否有旧状态；
- 是否锁定穿搭；
- 是否允许换装；
- 换装理由；
- 当前活动与地点；
- 最终穿搭摘要；
- 媒体 ID；
- 是否提交成功。

日志不应记录敏感配置或完整密钥。诊断重点是“决策与结果”，而不是暴露提供方信息。

可增加以下指标：

- 同日人物照片数量；
- 同日换装次数；
- 无理由换装拦截次数；
- 连续性状态读取/解析失败次数；
- 图片失败后状态未提交次数。

## 14. 上线步骤

实施时建议分阶段进行：

1. 完成连续性服务及单元测试；
2. 接入聊天自拍，验证同一会话连续三张；
3. 接入主动自拍，验证与聊天自拍共用状态；
4. 跑完整构建与回归测试；
5. 部署前备份当前运行版本和设置；
6. 部署并重启服务；
7. 检查服务状态与错误日志；
8. 初始化当天基准穿搭；
9. 用“街上 → 图书馆 → 图书馆内”验证默认锁定；
10. 用“去健身/洗澡后”验证合理换装；
11. 观察至少一个完整自然日并确认跨日重置。

建议实现提交顺序：

1. `test/continuity-contract`：先加入连续性决策与竞态测试；
2. `feat/continuity-state`：加入状态模型、时区日期键和串行锁；
3. `feat/director-continuity`：扩展导演输入输出及降级约束；
4. `feat/replier-continuity`：接入聊天自拍；
5. `feat/proactive-continuity`：接入主动自拍；
6. `chore/continuity-observability`：补齐元数据、日志和指标。

每一步都在当前功能分支内形成独立提交，便于审查和逐步回退；本方案阶段只提交文档，不执行上述实现。

## 15. 回滚方案

1. 保留部署前运行版本；
2. 连续性服务通过依赖注入接入，便于单点移除；
3. 状态使用独立版本化设置键，回滚旧代码时不会影响旧逻辑；
4. 若出现异常，先关闭连续性注入，再回滚运行版本；
5. 保留媒体元数据和连续性状态用于复盘，不必删除；
6. 回滚后验证文字聊天、图片生成和主动动态均恢复正常。

## 16. 验收标准

### 必须满足

- 同一天、同一段普通活动中连续生成至少 3 张人物照片，服装颜色、单品和层次一致；
- 从街上到图书馆等普通地点变化不换装；
- 用户明确要求换装时能换，并在后续照片中延续新穿搭；
- 洗澡、睡觉、运动等合理转换允许换装；
- 活动与地点和当前 Life/World 状态一致；
- 服务重启后仍延续当天穿搭；
- 图片或媒体保存失败不污染状态；
- 聊天自拍和主动自拍共享同一状态；
- 次日第一张照片不被前一天穿搭硬锁定；
- 所有相关现有测试通过。

### 不属于本次范围

- 对已经生成的旧照片进行重绘；
- 跨多日自动规划完整衣橱；
- 基于洗衣、天气、库存管理真实衣物；
- 强制聊天内普通纯场景图出现 SOOYA 本人（主动链路已无纯场景类型）；
- 仅靠视觉识别反向解析旧照片中的所有服装细节。

## 17. 推荐最终决策

采用“**每日持久状态 + 默认锁定 + 白名单换装 + 最终提示硬约束 + 成功后提交**”的方案。

它能直接解决当前连续两张照片衣服不一致的问题，同时保留正常生活中的换装自由。关键不是让图片模型自己“记住”，而是由服务端维护可审计的当天状态，并在每次生成前后控制状态读取、约束和提交。
