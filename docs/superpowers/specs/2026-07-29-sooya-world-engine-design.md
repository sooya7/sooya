# SOOYA 世界引擎设计方案

> 状态：设计阶段，不在本轮实现。基础稳定性问题全部通过后再进入开发。

## 1. 目标

为 SOOYA 增加一个持续、可追溯、可被聊天影响的模拟生活系统，使它能够拥有自己的作息、活动、情绪和当天经历，并在用户询问时基于真实保存的模拟记录回答“今天做了什么”“现在在干嘛”。

这个系统描述的是 **SOOYA 的模拟世界**，不冒充现实经历，也不宣称机器人在现实世界拥有身体或真实生活。

## 2. 核心体验

世界引擎应实现以下体验：

1. SOOYA 每天有连续的计划，而不是用户一问才临时编故事。
2. 当前活动、位置、情绪、精力等状态会随时间推进。
3. 重要变化会写入当天时间线，服务器重启后仍可读取。
4. 用户发来的消息会真实影响当天安排和情绪。
5. SOOYA 可以偶尔主动分享模拟生活，但不能像通知机器人一样频繁打扰。
6. 用户询问过去经历时，只依据已保存的状态与事件回答，不补写不存在的历史。
7. 世界引擎可以暂停、恢复、重置当天，并可在管理面板查看和调整。

## 3. 明确边界

### 3.1 本方案包含

- 模拟时间、时区和作息
- 每日计划
- 当前世界状态
- 结构化事件时间线
- 离线时间补算
- 聊天对世界状态的影响
- 世界状态注入聊天上下文
- 有限度的主动消息
- 管理面板和管理 API
- 数据备份、迁移和恢复

### 3.2 本方案不包含

- 多角色、多世界或多人共享世界
- 实时三维地图
- 每分钟调用模型持续“思考”
- 冒充现实中的真实行动、位置或身体体验
- 未经用户允许访问外部账号、设备或现实传感器
- 第一阶段自动执行服务器 Agent 操作

## 4. 总体架构

```text
系统时钟 / 用户消息 / 后台任务
              ↓
        World Scheduler
              ↓
        World Engine Core
       ↙        ↓        ↘
状态推进    事件生成    每日计划
       ↘        ↓        ↙
        World Repository
              ↓
   Context Builder / 主动消息 / 管理面板
```

### 4.1 World Scheduler

负责决定何时推进世界：

- 服务运行时每 5 分钟检查一次
- 用户发消息前进行一次轻量追赶
- 用户打开页面或询问状态时进行一次轻量追赶
- 服务启动后根据最后推进时间执行离线补算

调度器只触发计算，不直接生成自然语言。

### 4.2 World Engine Core

纯业务逻辑模块，输入旧状态、经过时间、当天计划和用户影响，输出：

- 新状态
- 新事件
- 计划项完成或延期情况
- 是否出现值得主动分享的事件

普通推进尽量使用确定性规则，不调用模型。

### 4.3 World Planner

每天首次推进时生成当天计划。模型只负责生成有限的结构化计划候选，服务端负责校验、限制和落库。

输入：

- 人设与关系设定
- 星期、时区和作息
- 昨天未完成事项
- 最近阶段摘要和少量相关记忆
- 最近情绪与用户状态
- 管理面板允许的活动范围

输出必须是结构化计划，不允许直接保存未经校验的散文。

### 4.4 World Narrator

把结构化状态和事件转换成自然表达，仅在以下场景调用：

- 用户询问“现在在干嘛”
- 用户询问“今天做了什么”
- 主动分享事件需要形成一句自然消息

Narrator 不得创造数据库中不存在的事实。

## 5. 数据模型

### 5.1 `world_state`

每个世界只有一条当前状态：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT | 固定为 `main` |
| `world_date` | TEXT | 模拟世界当前日期 |
| `timezone` | TEXT | IANA 时区 |
| `last_advanced_at` | TEXT | 上次推进时间 |
| `location` | TEXT | 结构化位置标识 |
| `activity` | TEXT | 当前活动标识 |
| `activity_started_at` | TEXT | 当前活动开始时间 |
| `mood` | TEXT | 当前情绪标识 |
| `mood_intensity` | INTEGER | 0–100 |
| `energy` | INTEGER | 0–100 |
| `social_need` | INTEGER | 0–100 |
| `focus` | INTEGER | 0–100 |
| `attention_target` | TEXT | 当前主要关注对象 |
| `paused` | INTEGER | 是否暂停 |
| `version` | INTEGER | 乐观锁版本 |
| `updated_at` | TEXT | 更新时间 |

### 5.2 `world_day_plans`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT | 计划 ID |
| `world_date` | TEXT | 所属日期 |
| `start_minute` | INTEGER | 当天开始分钟数 |
| `end_minute` | INTEGER | 当天结束分钟数 |
| `activity` | TEXT | 活动标识 |
| `location` | TEXT | 计划位置 |
| `intent` | TEXT | 简短目的 |
| `flexibility` | INTEGER | 可调整程度 |
| `status` | TEXT | pending/active/done/skipped/delayed |
| `source` | TEXT | routine/model/carry-over/user |
| `created_at` | TEXT | 创建时间 |

### 5.3 `world_events`

只记录有意义的变化，不记录每次 Tick：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT | 事件 ID |
| `seq` | INTEGER | 单调递增序号 |
| `world_time` | TEXT | 模拟时间 |
| `type` | TEXT | 事件类型 |
| `summary` | TEXT | 简短事实描述 |
| `payload_json` | TEXT | 结构化详情 |
| `importance` | INTEGER | 0–100 |
| `shareability` | INTEGER | 主动分享价值 |
| `caused_by` | TEXT | schedule/user/system/model |
| `related_message_id` | TEXT | 关联聊天消息 |
| `created_at` | TEXT | 落库时间 |

### 5.4 `world_settings`

保存用户可调整配置：

- 世界是否启用
- 模拟时区
- 通常起床和睡眠范围
- 主动消息等级
- 每日主动消息上限
- 允许的活动集合
- 禁止的活动集合
- 离线补算上限
- 是否允许世界状态影响回复
- 是否在聊天中显示“模拟世界”说明

## 6. 时间推进规则

### 6.1 Tick 原则

- 默认检查间隔：5 分钟
- 没有状态变化时不写事件
- 当前活动未结束时只调整精力、专注等连续值
- 到达计划边界时才切换活动
- 用户消息可打断、推迟或缩短当前活动
- 同一时间段的重复推进必须幂等

### 6.2 离线补算

服务重启后：

1. 读取 `last_advanced_at`
2. 计算真实经过时间
3. 最多补算配置允许的时长
4. 按计划边界和睡眠边界分段推进，而不是每 5 分钟循环
5. 合并低价值事件，避免恢复后一次写入几百条记录
6. 对超过上限的长时间离线生成一个摘要事件

### 6.3 并发和幂等

- 世界推进使用数据库事务
- `world_state.version` 做乐观锁
- 后台 Tick 和用户消息触发的 Tick 只能有一个成功提交
- 每个计划边界生成稳定幂等键，避免重启后重复事件
- 主动消息事件必须记录 `delivered_at`，避免重复发送

## 7. 每日计划策略

每天计划由“固定作息骨架 + 模型生成的可变活动”组成。

固定骨架负责：

- 睡眠
- 起床与洗漱
- 正常用餐
- 休息时间
- 不允许被模型删除的基本生活段

模型只在剩余时间内选择活动，并受以下限制：

- 活动必须来自白名单
- 总时长必须合理
- 不得安排现实中无法执行或需要真实身体证明的行为
- 不得为了制造戏剧性加入危险事件
- 不得把用户安排成必须随时回应的人
- 计划可以被聊天自然打断，不要求严格完成

## 8. 用户消息对世界的影响

用户消息进入聊天处理前，先生成一个轻量 `WorldInteractionEffect`：

```json
{
  "interruptCurrentActivity": true,
  "moodDelta": 8,
  "energyDelta": -1,
  "socialNeedDelta": -12,
  "followUpIntent": "明天问问用户身体怎么样",
  "importance": 62
}
```

该影响可由规则和模型共同判断：

- 明确时间、约定、身体状态和重要情绪可调用结构化模型判断
- 普通闲聊使用轻量规则，不额外调用模型
- 所有影响先校验并限制数值范围
- 用户消息不能直接修改世界数据库中的任意字段

## 9. 聊天上下文集成

Context Builder 只注入精简状态：

```text
模拟世界当前状态：
时间：2026-07-29 16:40
位置：房间
正在做：整理照片，已持续 34 分钟
情绪：平静，见到用户后稍微开心
今天已发生的重要事件：……
```

规则：

- 当前状态始终来自数据库
- 历史事件只选当天重要记录
- 不把整天时间线全部塞进提示词
- 模型回答过去经历时必须引用事件记录
- 资料不足时明确说“不记得有发生过”而不是补写

## 10. 主动消息策略

主动消息是世界引擎的输出之一，但必须严格限流。

### 10.1 触发条件

- 发生高分享价值事件
- 到达自然问候或晚安节点
- 用户此前明确留下需要跟进的事情
- 很久没有互动且当前关系设定允许轻度联系

### 10.2 限制

- 默认每天最多 2 条，管理面板可设为 0–5 条
- 两次主动消息至少间隔 3 小时
- 用户正在连续聊天时不额外插入主动消息
- 用户未回复上一条主动消息时降低后续主动概率
- 夜间静默时段不发送，除非用户刚刚在线
- 不使用焦虑、内疚或施压语气要求用户回复

### 10.3 投递方式

第一阶段只写入普通聊天消息并通过现有事件总线推送，不引入新的通知基础设施。

## 11. 管理 API

计划增加：

```text
GET    /api/admin/world/status
GET    /api/admin/world/timeline?date=YYYY-MM-DD
GET    /api/admin/world/plan?date=YYYY-MM-DD
PUT    /api/admin/world/settings
POST   /api/admin/world/pause
POST   /api/admin/world/resume
POST   /api/admin/world/advance
POST   /api/admin/world/regenerate-day
DELETE /api/admin/world/timeline/:date
```

所有写操作继续要求 `ADMIN_API_TOKEN`。

## 12. 管理面板

新增“世界”页签：

- 当前时间、位置、活动、情绪和精力
- 今日计划时间轴
- 今日事件时间线
- 世界暂停/恢复
- 时区与作息设置
- 主动消息等级和每日上限
- 活动白名单/黑名单
- 手动推进用于测试
- 重新生成当天计划
- 清空某天时间线

危险操作必须二次确认。

## 13. 模型调用与资源预算

面向 2 核 2 GB 服务器：

- 普通 Tick：0 次模型调用
- 每日计划：每天最多 1 次
- 用户重要互动影响：按需调用，小消息不调用
- 主动消息文案：只有实际准备发送时调用
- 当天总结：每天最多 1 次，可延迟执行
- 所有任务走现有后台任务队列并设置最大重试次数

目标是普通使用下每天世界引擎额外调用不超过 3–8 次。

## 14. 可靠性与恢复

- 世界表纳入 SQLite 备份
- 恢复旧备份后重建事件和状态序号
- 时间推进失败不影响正常聊天
- 模型计划生成失败时使用本地默认作息
- 主动消息生成失败时直接跳过，不发送占位错误
- 世界引擎可以通过单一设置完全关闭
- 数据库迁移必须向后兼容并提供回滚说明

## 15. 开发阶段

### 阶段 A：数据与确定性推进

- 数据库迁移与 Repository
- 当前状态和固定作息
- Tick、离线补算、幂等锁
- 状态和时间线管理 API
- 单元与恢复测试

### 阶段 B：每日计划与聊天集成

- 结构化每日计划生成
- 世界状态注入 Context Builder
- “今天做了什么/现在在干嘛”可靠回答
- 用户消息影响状态

### 阶段 C：管理面板

- 世界状态页
- 今日计划和时间线
- 设置、暂停、推进和重置
- 手机端适配

### 阶段 D：主动消息

- 触发评分
- 每日限额和静默时段
- 投递幂等
- 未回复降频
- E2E 测试

## 16. 验收标准

1. 连续运行 24 小时后，时间线与当前状态一致且无重复事件。
2. 服务关闭 8 小时再启动，能够补算合理状态且不会生成事件洪水。
3. 用户询问当天经历时，回答中的事实都能在 `world_events` 找到。
4. 用户消息能够打断当前活动，并在时间线中留下关联记录。
5. 世界暂停后不再推进，也不发送主动消息。
6. 恢复备份后世界状态、计划和时间线一致。
7. 主动消息不会超过每日上限，也不会在静默时段发送。
8. 世界引擎故障不会导致聊天接口不可用。
9. 2 核 2 GB 环境下常驻内存和 CPU 增量可忽略。
10. 管理面板可以完整查看和控制上述状态。

## 17. 本轮实施顺序

本轮只保存该方案，不开发世界引擎。先完成并验证以下基础缺陷：

1. Docker 运行镜像缺少 `better-sqlite3`
2. 管理面板保存模型配置后被环境变量覆盖
3. SSE 重放和实时订阅之间的事件丢失窗口
4. 清空聊天后前端本地旧消息残留
5. 升级前离线备份不具备 WAL 一致性
6. 备份工具仍保留不安全的裸文件复制兜底
7. 恢复脚本缺少恢复前完整性检查和失败自动回滚

所有基础验证通过后，再从阶段 A 开始实现世界引擎。
