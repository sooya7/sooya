# “她的生活”管理页整合与只读观察设计

日期：2026-08-09
状态：已确认

## 背景

当前生活管理能力分散在两个页面：

- 管理中心 `/admin/life` 中的 `LifePanel` 同时展示此刻状态、主动开口、计划、规则和多类记录，并提供推进、创建计划和修改计划等操作。
- 独立页面 `/admin/life/console` 通过八个同级标签展示总览、身体状态、计划、事线、事件、地点、主动开口和天气，并提供多种人工干预操作。

这造成三类问题：

1. 两套入口与重复信息让用户难以判断应该在哪一层查看或管理生活状态。
2. 信息、表单、诊断和操作具有近似的视觉权重，桌面端形成“卡片堆叠”，移动端出现横向标签、过长页面和破碎表单。
3. 页面把用户放在“操控角色生活”的位置，与“角色的心情和事件应自行发展”的产品目标冲突。

## 目标

- 只保留 `/admin/life` 一个用户可见入口。
- 将页面定位从“生活控制台”改为“生活观察页”。
- 心情、身体状态、计划、事线、地点与事件在页面中全部只读，由生活引擎自行发展。
- 联系边界仍可编辑，因为它描述用户愿意怎样被联系，而不是改变角色的生活。
- 保留现有服务端读写 API、数据库结构和生活引擎行为；本次只改变管理页面的可见能力与调用方式。
- 桌面端和移动端使用同一信息顺序，无内层侧栏、无横向标签、无卡片堆叠。

## 非目标

- 不修改 LifeEngine 或 Life V2 的状态推进、评分、计划、事线、地点、天气和事件生成逻辑。
- 不删除、禁用或改变现有 `/api/admin/life/*` 写接口。
- 不改变聊天页中的生活状态展示。
- 不重构管理中心的其他页面或全局导航。
- 不新增图表、拖拽、批量操作或新的生活数据模型。

## 产品原则

### 观察而非操控

页面可以解释角色正在做什么、可能做什么、为什么没有主动联系，以及生活如何自然延续，但不能提供下列操作：

- 强制推进生活状态；
- 调整或重置身体数值；
- 创建、开始、暂停、完成或取消计划；
- 创建、暂停、解决或归档事线；
- 新增、修改、删除或强制切换地点和城市；
- 人工改变心情或制造生活事件。

这些后台 API 保持不变，但新页面不渲染对应控件，也不发出对应写请求。

### 解释优先

原始枚举和内部状态不直接成为主文案。首屏使用自然语言解释状态，例如：

- “抱着被子睡 · 心情安静”；
- “预计 07:30 自然醒来”；
- “仍在睡眠中，并且现在属于安静时段”；
- “取决于天气和心情”；
- “由她自行决定”。

内部 kind、状态码和调试字段只在确有诊断价值的只读详情中出现。

### 渐进披露

首屏只展示高频信息。身体指标、地点天气、历史记录和联系边界位于下方折叠区，避免所有能力同时争夺注意力。

### 少卡片、少按钮

- 页面使用字号、留白和细分隔线建立层级。
- “此刻”“主动开口”和每条记录不再分别套卡片。
- 只读列表不伪装成按钮。
- 页面默认没有主操作按钮；只有展开“联系边界”并修改后才出现“保存联系边界”。

## 信息架构

### 1. 页面标题

标题为“她的生活”，说明文案强调这是观察页。显示“刚刚更新”或上次成功更新时间，说明状态会随时间自行变化。

删除 `LifeAdminLink` 及“打开完整生活管理”入口。

### 2. 此刻

常驻首屏，包含：

- 当前活动与心情；
- 角色本地时间；
- 活动已持续多久、预计何时自然变化；
- 只读进度条；
- 主动开口状态及原因；
- 今日已主动联系数量。

不显示“立即推进”或任何状态干预操作。

### 3. 今天可能会做

展示最多三个当前或待定计划，文案强调它们是角色自己的安排或可能性，而不是用户任务清单。

- 不显示“添加计划”。
- 不显示“开始、暂停、继续、完成”。
- 状态以自然语言呈现，例如“上午 · 可能”“尚未决定”“正在进行”。
- 无计划时显示“她还没有决定接下来做什么”，不提供创建入口。

### 4. 正在发展的事

展示开放事线及进度，帮助用户理解生活连续性。事线只读，不提供创建、暂停、解决或归档操作。

### 5. 身体与节律

默认折叠。展开后只读展示精力、饥饿、压力、社交需求、孤独、好奇、舒适、专注与睡眠债。

- 使用语义标签和数值，不提供加减按钮。
- 不提供重置。
- Life V2 未启用时说明“身体状态未启用”，不提供修复或初始化操作。

### 6. 地点与天气

默认折叠。展开后展示：

- 当前城市与地点；
- 当前天气与缓存状态；
- 旅行状态；
- 近期预报；
- 环境如何影响当前选择的简短说明。

不提供地点或城市的新增、编辑、删除、激活、旅行或强制切换操作。

### 7. 生活记录

默认折叠，将原先分散的内容按时间组织：

- 做过的事；
- 自然发生的生活事件；
- 主动分享尝试与结果。

同一时间线优先展示用户可理解的描述，必要时使用轻量筛选切换“全部、事件、分享”，但不恢复八个同级标签。

### 8. 联系边界

默认折叠，是页面唯一可编辑区域。保留以下设置：

- 是否允许主动联系；
- 用户安静多久后角色可以主动开口；
- 每日主动联系上限；
- 静默时段；
- 主动分享模式。

标题和帮助文案必须明确：这些设置只决定角色什么时候、以什么方式联系用户，不改变角色的心情、计划、地点或事件。

## 交互行为

- 首屏数据加载完成后每 30 秒自动刷新。
- 自动刷新不得改变滚动位置、折叠状态或正在编辑的联系边界表单。
- 详细折叠区在首次展开时加载对应只读数据；加载过的数据可以在当前页面会话中复用并按需刷新。
- 折叠区使用原生按钮语义与 `aria-expanded`、`aria-controls`；点击区域至少 44×44 像素。
- 桌面端使用受控内容宽度，移动端保持同一纵向顺序。
- 页面不引入内层侧栏、横向滚动标签或悬浮操作条。
- 联系边界使用显式保存。修改后沿用管理中心已有的未保存离开提醒。

## 路由整合

- `AppShell` 不再为 `/admin/life/console` 单独渲染 `LifeAdminPage`。
- `/admin/life` 由现有 `AdminPanel` 的 `life` 分区渲染统一观察页。
- 旧地址 `/admin/life/console` 进入 `AdminPanel` 后由现有管理路由归一逻辑替换为 `/admin/life`，不产生第二套页面或新的重定向循环。
- 删除页面中的完整控制台入口后，用户可见导航只剩管理中心侧栏中的“她的生活”。

## 组件边界

统一页面由一个协调组件和若干聚焦的展示组件组成：

- `LifePanel`：加载首屏数据、管理自动刷新、折叠状态、局部错误和联系边界草稿。
- `LifeNowSummary`：此刻状态、进度与主动开口原因。
- `LifePlansPreview`：只读展示最多三个计划。
- `LifeThreadsPreview`：只读展示开放事线。
- `LifeDisclosureSection`：统一折叠交互、加载与错误状态。
- `LifeVitalsView`：只读身体与节律。
- `LifeEnvironmentView`：只读城市、地点、旅行与天气。
- `LifeHistoryView`：合并活动、事件与主动分享记录。
- `LifeContactBoundaryForm`：唯一写入组件，只调用联系边界设置接口。

`LifeAdminPage.tsx` 中仍有价值的只读格式化与展示逻辑迁移到这些组件或相关视图辅助模块。完成迁移并覆盖测试后删除独立页面，避免继续维护两套生活界面。

## 数据流与 API 边界

### 首屏

复用现有读取能力，不新增服务端接口：

- `GET /api/admin/life` 提供 snapshot、plans、log、events、proactive、reachOut 与 settings。
- `GET /api/admin/life/overview` 补充 vitals、location、weather、activePlan、openThreads 与 recentEvents。

页面协调组件可以并行读取两者，并以 `/api/admin/life` 的联系边界设置作为表单来源。

### 折叠详情

继续使用现有只读接口：

- `GET /api/admin/life/vitals`
- `GET /api/admin/life/threads`
- `GET /api/admin/life/plans`
- `GET /api/admin/life/events`
- `GET /api/admin/life/proactive`
- `GET /api/admin/life/locations`
- `GET /api/admin/life/cities`
- `GET /api/admin/life/travel`
- `GET /api/admin/weather/status`
- `GET /api/admin/weather/forecast`

统一观察页不调用写入型的 `POST /api/admin/weather/refresh`；天气刷新继续由现有后台流程或其他管理工具负责。

### 唯一页面写入

`PUT /api/admin/life/settings` 继续用于保存联系边界。前端只提交 `reachOut`、`quietGapMinutes`、`maxReachOutsPerDay`、`silentFrom`、`silentTo` 和 `proactiveMode`。

### 保留但不调用的接口

现有推进、身体调整、计划、事线、地点和城市写接口保持原有合同与行为。统一观察页不得导入或调用相应客户端 mutation 方法。服务端测试继续覆盖这些接口，避免本次 UI 改造意外改变后台能力。

## 加载、错误与空状态

- 首屏首次加载显示与最终排版相同高度的轻量骨架，避免布局跳动。
- 首屏加载失败时显示原因与“重新读取”操作，不显示虚构状态。
- 折叠详情独立处理加载和错误；一个模块失败不清空其他模块。
- 已有数据刷新失败时保留旧数据，显示“更新失败，上次更新于……”和局部重试。
- 空计划、空事线、空记录使用解释性文案，不提供创建操作。
- 联系边界保存失败时在表单附近显示原因与恢复方式；保存成功后使用 `aria-live="polite"` 提示。

## 视觉与响应式规则

- 保持现有 SOOYA 暖色主题和语义色 token，不采用技能搜索建议中的通用蓝色或纯暗色方案。
- 使用 4/8 像素间距系统和稳定字号层级，正文不小于 16px 的移动端可读基线。
- 首屏使用一个连续页面表面；模块之间以留白和细分隔线区分，不为每段内容增加阴影卡片。
- 状态不能只靠颜色表达，文字必须明确说明“暂不、可联系、加载失败”等语义。
- 375px 宽度下不得出现横向页面滚动，折叠标题与表单控件保持至少 44px 触控高度。
- 自动刷新和折叠过渡尊重 `prefers-reduced-motion`。

## 测试策略

### 组件测试

- 首屏渲染此刻、主动开口原因、最多三个计划和开放事线。
- 页面不存在“打开完整生活管理、立即推进、添加计划、开始、暂停、完成、调整、重置、切换地点”等控件。
- 空计划、空事线、Life V2 未启用和空记录文案正确。
- 折叠区按需加载，失败只影响当前区域。
- 30 秒刷新不重置折叠状态、滚动位置或未保存的联系边界表单。
- 联系边界保存只提交允许字段。
- 页面不会调用任何生活干预 mutation 方法。

### 路由测试

- `/admin/life` 渲染统一观察页。
- `/admin/life/console` 被归一为 `/admin/life`。
- 删除完整控制台入口后仍可通过管理侧栏进入页面。

### 服务端回归

- 现有 Life Admin 读取测试保持通过。
- 现有写接口测试保持通过，证明 API 未因页面只读化而被删除或改变。
- 联系边界设置测试保持通过。

### 响应式与可访问性验证

- 在 375px、768px、1024px 和 1440px 检查无横向溢出和无内层横向标签。
- 验证键盘可以依次进入每个折叠标题和联系边界表单。
- 验证 `aria-expanded`、焦点环、错误提示与成功提示。
- 验证 reduced-motion 下无非必要过渡。

## 完成标准

- 用户只通过 `/admin/life` 查看生活信息。
- 页面首屏清楚回答“她现在怎样、接下来可能做什么、为什么没有主动联系”。
- 所有生活发展数据在页面中只读，页面不存在人工干预入口或干预请求。
- 联系边界仍可编辑并可靠保存。
- 现有后台 API 保持可用且合同不变。
- 桌面端和移动端均没有卡片堆叠、内层侧栏或横向标签造成的信息拥挤。
